## 판정

확대·이동·배경 변경 중 중복 렌더링과 동기 PNG 변환을 줄였습니다. 현재 형태·재질·그림자·해상도 설정과 UI를 유지했습니다. PC 실제 GPU 검증과 모바일 에뮬레이션 검증을 마쳤습니다. **실제 휴대전화 검수는 미실시이며, 콜드 초기화와 새 작품 교체에 50ms 이상 작업이 남아 있습니다. 모든 합격 조건을 무조건 충족했다고 판정하지 않습니다.** 실사 재질·조명 추가나 공개 배포는 하지 않았습니다.

## 측정 방법과 해석

`performance.now()` 함수 계측, PerformanceObserver longtask, requestAnimationFrame 간격, CDP Performance/Memory, 실제 Three.js `renderer.info`, WebGL2 GPU timer query를 사용했습니다. Chrome Performance에서 열 수 있는 CDP trace는 `results/{baseline,optimized}-{pc,mobile}/trace.json`입니다. 계측·trace 비용은 양쪽에 동일하게 적용했습니다.

`configure` 호출 수는 완성 렌더링 패스 진입 수입니다. 패스 내부의 개별 GL draw call 개수나 GPU 실행 시간과는 다릅니다. 함수 시간은 중첩되므로 합산하면 안 됩니다. `toBlob` 시간은 비동기 콜백까지의 대기시간이며, 같은 시간 동안 메인 스레드가 막혔다는 뜻이 아닙니다.

아래 시나리오 경과 시간은 조작·폴링·마지막 관찰 대기를 포함합니다. 관찰 대기: 최초 진입 700ms, 두 번째/닫기 450ms, 슬라이더·이동·배경·5개 작품 500ms, 저장 250ms, 정지 1000ms입니다. 순수 렌더링 시간과 구별해야 합니다. FPS는 이 PC의 약 180Hz rAF 샘플 평균이며 실제 스마트폰 FPS를 뜻하지 않습니다. 긴 멈춤이 p95에서 빠질 수 있어 최대 프레임과 longtask도 함께 표시했습니다.

## P0에서 확인한 병목

1. 슬라이더와 실제 포인터 이동이 숨겨진 카드까지 더럽혀 매번 고해상도 카드 export와 원래 화면 재렌더를 발생시켰습니다. `drawPhoto`, `renderCard`, `render/export` 호출 수가 증거입니다.
2. 배경 변경은 원래도 메시를 다시 만들지 않았습니다. 실제 병목은 닫힌 사진 미리보기에서 실행되는 `browserPreview`의 1200px export와 동기 `toDataURL`이었습니다. PC 최대 단일 PNG 64.6ms, background 단계 longtask 3개였습니다.
3. 처음 생성하는 잔금 텍스처의 픽셀별 반복 seed 계산이 컸습니다. 원본 5개 교체의 최대 longtask 4143.0ms. 최적화 후 최대 409.0ms로 줄었지만 50ms 이하가 된 것은 아닙니다.
4. 같은 크기에도 framebuffer 크기를 반복 지정했고, 카메라만 바뀌어도 그림자를 다시 계산했습니다. 렌더러는 원래부터 재사용됐고, 정지 상태 dirty 루프도 원래 불필요한 3D 렌더를 하지 않았습니다. 양쪽 idle 패스 0회입니다.
5. 배경 JPEG는 원래부터 한 번 디코딩하고 재사용했습니다. `imageLoads`는 로컬 load+decode 지연, `imageDecode`는 브라우저 decode 대기시간입니다. 순수 JPEG 디코더 CPU 시간을 분리해 측정한 값은 아닙니다. 배경 전환 중 새 디코딩이 핵심 병목이라는 증거는 없었습니다.

함수별 호출·합계·최대·p95는 각 시나리오 JSON에 모두 있습니다. `drawPhoto/browserPreview/TodakPhoto.render/export/rebuild/configure/toDataURL/backgroundComposite/setStage/thumbNow/itemFields/shelfAddCurrent/lsSave/renderShelf`를 계측했습니다.

## 구현한 구조

- 형태·재질·기본 유약 맵·완성 투명 레이어를 분리하고 각 LRU를 2개로 제한했습니다. 실제 반경·속 형태·높이·바닥·입구·그림·조각·유약·무늬·불투명도·담그기를 키에 포함했습니다.
- 현재 사진 배경 3종의 3D 조명은 동일합니다. 도자기와 접촉 그림자가 포함된 투명 레이어를 보관하고 배경을 따로 합성합니다. 투명 진열장 컷아웃·360도 감상은 별도 키로 구분합니다. 조명 모드·작품·회전이 바뀌면 필요한 그림자를 갱신합니다.
- 안전하게 포함된 이미지의 확대·이동 중에는 캐시된 이미지 변환을 사용합니다. 잘림 위험·큰 배율 변경은 기존 3D 경로로 처리합니다. 조작 종료 145ms 후 정확한 전체 품질 렌더를 수행합니다. 저장은 미리보기 캐시를 확대해 쓰는 방식이 아닙니다.
- 잔금 cell seed를 재사용하고 동일 산술을 유지합니다. 무거운 새 유약 맵은 Worker+OffscreenCanvas로 만들고, 기본 유약 맵과 사용자 그림을 분리합니다. 같은 요청을 합치며 한 작업+최신 대기 작업만 유지합니다. Worker 실패 시 원래 품질의 동기 대체 경로로 돌아갑니다.
- 캔버스 사이즈 변경과 그림자 갱신은 필요한 경우에만 수행합니다. 그림자 해상도·픽셀 비율·메시 분할·물리 재질 값은 낮추지 않았습니다.
- 숨겨진 카드 렌더와 배경 선택 시의 미리보기 PNG 생성을 제거했습니다. 미리보기와 공유는 toBlob/object URL을 사용하고, 닫기·재열기의 오래된 비동기 결과를 막고 URL을 해제합니다.
- 완성 원본은 사진을 기다리지 않고 기존 시점에 보관합니다. 최초 임시 썸네일은 GPU 화면 읽기를 하지 않고 사진 준비 후 정상 투명 썸네일로 바꿉니다. 준비 전에 새 작업으로 떠나도 원본이 남는지 검증했습니다. 영구 미완료 상태로 무거운 작업을 쌓아 두지 않습니다.
- 빌드에 Worker 파일 복사와 텍스처·Worker 버전 해시를 연결했습니다. 독립된 전체 빌드를 실행했고, 생성 HTML은 자산 해시와 줄바꿈을 제외하면 검증본과 같습니다.

| GPU texture 수, 6묶음 모두 | 8 | 11 |
| GC 후 JS heap, 처음→마지막 MiB | 6.19→6.70 | 6.36→6.88 |
| 마지막 4묶음 heap 범위 MiB | 0.172 | 0.175 |
| 닫은 뒤 남은 미리보기 object URL | 0 | 0 |

개선본은 2개 캐시를 보관하므로 자원 수가 조금 큽니다. 반복할수록 GPU 객체가 증가하는 현상은 관찰하지 못했습니다. `clearCache()` 후 형태/재질/맵/프레임 캐시·소유 텍스처 참조는 모두 0입니다. 유지하는 장면/환경 리소스는 geometry 3, texture 5입니다. 측정된 프레임 캐시+합성 캔버스 예상 버퍼는 약 45.8MiB로 제한됐습니다.

JS heap에는 Canvas 외부 메모리, Worker 전체 메모리, GPU VRAM이 모두 포함되지 않습니다. GPU 객체 수는 실제 VRAM 바이트가 아닙니다. 따라서 이 유한 반복 검사만으로 모든 기기의 장시간 메모리 누수가 없다고 단정하지 않습니다.

## 품질·기능 회귀

- 같은 작품 5개 × 배경 3종/바닥 시점 = 20장. 형태·속 형태·높이·바닥 데이터 일치, 투명 경계 alpha 차이 0.
- 전체 런타임 유약 목록과 직접 선택 색상, 유광/무광, 없음/점박이/잔금, 담그기 조합 162개 비교. 최대 채널 차이 3/255, 최대 평균 절대 오차 0.0268/255, alpha 차이 0. 대부분 기존 주요 사진은 픽셀 일치하고 잔금/색 합성에서 미세한 반올림 차이가 있습니다. 완전히 byte-identical한 모든 이미지라고 주장하지 않습니다.
- 잔금 color/height/roughness 맵은 64px·256px에서 원본과 byte-identical. 메시·텍스처 해상도와 입구/바닥 그림·조각을 유지했습니다. 원본 대비 새로운 검은 경계·깨짐·최종 흐림은 비교에서 관찰되지 않았습니다. 기존 원본 자체의 시각 문제를 새로 교정한 작업은 아닙니다.
- 모바일 에뮬레이션에서도 같은 5개 작품·20개 시점을 비교했습니다. alpha 차이 0, 최대 채널 차이 4/255였습니다. 실제 모바일 기기는 별도 검수해야 합니다.
+- 실제 저장 버튼으로 1080×1500 PNG 다운로드 확인. 브라우저 공유 대화상자를 외부에 전송하는 테스트는 하지 않았고 File 생성 경로는 유지했습니다.
- 저장 작품 5개 재열기·로컬 저장 후 새로고침·준비 전 이탈 검사 통과. 저장 원본 및 작업 중인 도자기가 바뀌지 않았습니다. 기존 소수 둘째 자리 저장 정밀도와 스키마를 변경하지 않았습니다.
- Worker 실패·WebGL 미지원 시 기존 대체 표시와 PNG 저장 검사 통과.
- 모바일 에뮬레이션 전체 제작→꾸미기→유약→가마→완성→360도→내 진열장 재열기, 두 소셜 진입 주소·정적 자산·피드백 창 열기/닫기 검사 통과. 운영 서버로 제출하는 동작은 실행하지 않았습니다.
- 인라인 스타일과 CSS 파일이 원본과 동일합니다. 배경 이미지·load-3d·저장 작품 읽기 파일도 그대로입니다. Supabase 연결 설정·호출 경로·기존 제작 알고리즘을 수정하지 않았습니다.

## 아직 남은 검수·제약

1. 실제 Android/iOS 브라우저·설치 앱·저사양 GPU·발열 조건은 미검증입니다. 모바일 최초 진입 개선은 아직 합격 판정하지 않습니다.
2. 초기 환경 생성·셰이더 준비와 새로운 작품의 첫 업로드/조각/합성에서 50ms 이상 작업이 남습니다. 5개 작품 교체 시 longtask 수가 증가했지만 최대 정지는 크게 짧아졌습니다. 다음 작업은 이 초기 비용의 단계별 비동기 준비를 검토하는 것이며, 사진 품질을 낮추지는 않아야 합니다.
3. 두 번째 진입·단순 닫기 경과 시간의 확실한 개선은 입증하지 못했습니다. 렌더 패스 감소만 확인됐습니다. 배경·슬라이더·실제 포인터 이동의 개선과 구별해야 합니다.
4. 실제 Supabase 서버 왕복, 시스템 공유 UI, 모든 과거 데이터의 전수 검수는 미실시입니다. 정적 연결 보존과 동일 스키마의 5개 저장 원본 복원까지만 검증했습니다.
5. 고품질 실사 재질·조명 추가 작업은 진행하지 않았습니다. 공개 사이트는 원래 커밋 그대로입니다.

## 변경 파일과 재현

실제 코드 9개는 `changed-files.json` 및 `changes.patch`에 있습니다.

| 파일 | 변경 목적 |
|---|---|
| index.html | 프레임·카드·썸네일·전환·저장 연계 |
| real-photo.js | 조작 중 캐시 사용, 미리보기/PNG 분리 |
| pottery-renderer.js | 형태·재질·맵·프레임 캐시와 GPU 자원 관리 |
| ceramic-surface.js | 동일 잔금 계산의 seed 재사용 |
| photo-texture-worker.js | 새로운 기본 유약 텍스처의 별도 스레드 계산 |
| ui-layout-preview/pottery-renderer.js | 기존 빌드가 최적화를 덮어쓰지 않도록 같은 렌더러 반영 |
| tools/optimize-photo-html.cjs | 기존 빌드 후 인라인 최적화 적용 |
| tools/build-studio-layout.cjs | HTML 최적화 연결 |
| tools/build-public-release.cjs | Worker 포함·종속 자산 해시 연결 |

패치를 별도 복사본에 실제 적용해 코드 내용 일치를 확인했습니다. Git 설정에 따라 줄바꿈은 정규화될 수 있습니다. 전체 빌드는 `build-check/`에서 실행했습니다. 이 하위 폴더는 별도 Git 저장소가 아니므로 검증 harness가 Git 파일 목록 대신 고정 커밋의 동일 런타임 목록을 공급했습니다. 나머지 실제 빌드 코드는 그대로 실행했습니다. 이는 배포나 원격 변경을 하지 않습니다.

로컬 확인:

~~~powershell
node photo-performance/serve.cjs
~~~

- 원본: http://127.0.0.1:8784/
- 개선본: http://127.0.0.1:8785/

최종 측정과 회귀 검사:

~~~powershell
node photo-performance/check-source.cjs
node photo-performance/validate-final.cjs
node photo-performance/validate-extra.cjs
node photo-performance/gpu-matrix.cjs
node photo-performance/regressions.cjs --built
node photo-performance/quality.cjs --mobile --quick
~~~

테스트는 설치된 Chrome/Playwright를 사용합니다. `setup.cjs`는 원본·개선 폴더를 다시 구성하므로 검토 중 실행하면 안 됩니다. 코드 적용 후에는 기존 `node tools/build-public-release.cjs`로 자산 해시와 Worker를 함께 조립해야 합니다. 공개 배포 명령은 이 작업에서 실행하지 않았습니다.
